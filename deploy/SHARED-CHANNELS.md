# Explicit shared-channel opt-in

Slack Connect is denied by default. An operator may propose an already approved ordinary channel in both `SLACK_CHANNEL_IDS` and `SLACK_SHARED_CHANNEL_IDS`. The shared list defaults to empty, must be a subset of the ordinary channel list and cannot overlap group DMs. Either channel mode can use this individual opt-in. In `all_joined` mode, other internal channels still require verified Bot membership; other external/shared channels remain denied. This does not grant Slack access, invite a bot, or change an existing connector restriction.

Before applying this configuration, verify the exact app/Bot identity, channel identity and type, workspace context and legitimate Bot membership through authorized means. Resolve existing access restrictions through their supported owner/admin process. An existing member requires no invitation. A private channel normally needs its existing member/authorized administrator to add an app through the channel's Integrations tab, subject to its policy. Do not automatically join/invite, add OAuth scopes, read via another credential to bypass a denial, or turn an unavailable shared channel into a different conversation.

Event ingress and the send-time Conversations API check independently enforce the shared opt-in. Wrong workspace, wrong channel, archived or pending-shared state, direct messages, unapproved group DMs and missing Bot membership remain denied. An event missing its shared flag does not bypass the send-time metadata check. The workspace/channel/member checks, literal trigger, human-only filters, fixed mention text, exact original thread timestamp, durable deduplication, rate gate and unknown-send handling remain in effect.

The channel permission covers the channel, including its top-level messages and threads; it is not a title/date-based thread filter. Existing sender rules remain unchanged. In particular, the outer workspace ID is not proof of an author's organization in a shared channel. Do not promise that all external people are excluded solely by that field. All channel members, including external participants, can see Bot replies and configured mention IDs. Review that exact exposure and trigger scope before enabling this opt-in; no message text is copied into the Bot's reply or persisted by this feature.

No extra OAuth scope is introduced by this code. A private channel uses the existing `groups:read`, `groups:history`, `message.groups` subscription and `chat:write`, provided the app is legitimately installed and the Bot is a verified member. Runtime settings and deployment authorization are separate from code publication. Keep existing configuration unchanged while the patch is under review.

Adding/removing shared permissions changes the policy fingerprint, cancelling pending events from the prior policy rather than replaying them under new access. Leaving this list empty preserves the previous fingerprint and ordinary-channel behavior. Roll back the permission by removing the shared ID (or disabling the Bot) and retaining the ledger; never clear deduplication state to force a resend.

References: [Slack Connect](https://docs.slack.dev/apis/slack-connect/), [apps in Slack](https://slack.com/help/articles/360001537467-Guide-to-apps-in-Slack), [app approval](https://slack.com/help/articles/202035138-Add-apps-to-your-Slack-workspace).
