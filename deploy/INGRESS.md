# Optional container ingress (approval required before activation)

This profile is an alternative to the host user service. Never run both against the same state. It does not replace the existing SSH deployment workflow or authorize any DNS, Tunnel, network, membership, credential, or service change.

Use the tested revision image, an inspected official Python image digest, the VM owner UID/GID, the existing private runtime file, and the existing private state directory. `compose.ingress.yml` publishes no host ports. The private runtime file is mounted read-only as a file, not placed in Docker's configured environment; the entrypoint rejects symlinks, wrong ownership/mode, duplicate or unexpected keys. The image build context contains only code. Runtime logs are disabled and no Docker socket is mounted. The process runs as the VM owner with no capabilities, a read-only root, limited memory/process count and a writable bot state mount.

Create a dedicated bridge `dcon-slack-ingress` only after approval. Attach only this bot and the specifically approved existing Tunnel connector; preserve the connector's original network and every existing route. No restart of an existing application is required for an additional runtime network connection. Connector recreation can lose an ad-hoc network attachment, so deployment must verify and restore the explicitly approved attachment before declaring ingress healthy. Do not edit or recreate an unrelated Compose stack to conceal this limitation. The bot is isolated from the original application network.

Proposed Tunnel rule shape (not applied): dedicated approved hostname, path regex `^/slack/events$`, service `http://slack-auto-mention:8765`. Preserve every other rule and the final 404 catch-all. Only that path is forwarded; `/healthz` stays internal. Confirm the hostname is unused and inspect the reviewed route diff immediately before saving. A browser login challenge, generic managed challenge, or Cloudflare Access login is incompatible with Slack's server webhook. Authenticate at the application with Slack HMAC verification; do not weaken an existing application policy. HTTPS terminates at Cloudflare and the existing authenticated Tunnel reaches the dedicated internal Docker network.

Before activation, keep `BOT_ENABLED=false` and `ALLOWLIST_VERIFIED=false`. Signed Slack URL verification is accepted while posting is disabled; health reports 503/not-ready. Verify real signatures, expected app/workspace, approved channel membership, scope set and exact recipients before setting the two activation flags. Set message.channels/message.groups, and message.mpim only when the fixed approved MPIM is actually readable/member-verified. No automatic joins, invites or new conversation creation. All other conversations and Slack Connect channels remain rejected.

The bot validates the raw-body HMAC and a five-minute timestamp window. Event IDs are durably deduplicated. Persistence failures are not acknowledged as success. Unknown send outcomes are held and never automatically retried; durable global Retry-After applies to subsequent events. Invalid signatures, oversized requests and unsupported paths are rejected. Uncaught startup/runtime errors stop the process, `restart: "no"` prevents a crash loop, and container health stays unhealthy when posting is disabled or the worker is stale. A verified deployment must retain the previous image and state, switch only this bot after checks, and stop/restore the previous tested bot image if readiness fails. Do not delete the ledger during rollback.

Rollback of an unverified first ingress: keep posting disabled, remove only the newly approved dedicated Tunnel route/DNS record and this bot's dedicated connector-network attachment, and leave all existing applications/routes unchanged. Do not expose the service first and add signature validation later.
